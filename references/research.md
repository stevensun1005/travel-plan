# 查价、排程与资料覆盖

## 报价要记录什么

| 项目 | 必要信息 |
| --- | --- |
| 航班 | 查价日，人数，往返/单程全程总价，机场、当地日期时刻、中转与总时长、舱等、行李、退改缺口、币种、来源 |
| 酒店 | 入住退房、晚数、人数/房间、房型，全住期总额、税/强制费、停车早餐另收与否、退款、来源 |
| 租车 | 指定车型/同级、座位、变速箱、年龄驾照资格、取还时刻、完整总价、青年费、保障/自付、责任险、税、里程、交车费和退款 |
| 活动 | 日期与目标场次、营业/休息日、预约窗口、票含什么、交通和退改；目标场次不等于已取得余位 |

价格状态用：已预订、指定条件查价记录、搜索页记录、官方常规价、预算估算、尚无报价、虚构演示。网页可访问不代表库存已核实，一次查价不叫持续实时价格。

用户指定Expedia等平台时遵循来源偏好；尽量核到完整往返/开口程汇总，不将单程选中价、其他日期或同城往返价冒充当前完整行程。涉及多城性价比、报价适用条件与景点详情时读 [多城市选择与景点详情](multi-city.md)。

具体门店与车型优先于品牌通用年龄规则。规则冲突就说明并继续取得门店确认或该年龄结算记录。加拿大完整驾照、多年驾龄不自动免青年费，双座敞篷也不天然更便宜。改变日期或租期需重新报价；48小时与多一小时可能不同计费。汇率按查价日央行汇率换算，是预算口径，不是结算承诺。

## 多平台比价

先问清楚：是否只要直飞、可接受几次转机、指定或排除的航空公司、舱等。比价只在满足这些条件的同一个产品之间进行。

| 类别 | 要查的平台 | 比什么 |
| --- | --- | --- |
| 机票 | 航空公司官网、Trip.com（携程国际站）、携程中文站、Booking.com、Expedia | 同一航班组合、两人（或全部人数）往返含税总价，**每人含1件随身行李箱**的最低票价档 |
| 酒店 | Vio、Expedia、Booking.com、Trip.com；携程中文站能看到价才算 | 同一酒店、同样入住退房和人数、全住期含税和强制费的总价；可退与不可退分开写 |

- 去哪儿、飞猪不在流程里：网页版查不了国际航线或要登录才给数据。别的平台要求登录、出验证码时，跳过并在来源里写明，不替用户登录、不绕验证。
- 随身行李：票价档写着不含随身行李箱（如 AC/美航/联航的 Basic）就不算这个档，取含随身行李的最低档；平台只给一个价时，点开票价详情确认行李。套餐里的机票是这种票时，按航司官网两档差价补上，在 note 里写清楚是补差估算。
- 汇率：外币报价按央行当日汇率换成旅行币种（加币用加拿大央行 Valet API），记下日期和来源；页面上同时显示原币价。`apply_quotes.py --fetch-fx` 会自动取汇率、换算、排序，并把选项金额设成最便宜那家、在 `source` 写上平台名。
- 记录：每个平台一条 `quotes`，含平台、金额、币种、查价日、链接和条件差异（可退/不可退、含早、要换房、不能改期）；平台上没有这个产品或没房也写一条 `available:false`。选项金额永远是最便宜那条，条件更差的便宜价要在 note 里说清楚（例如不能改期）。
- 链接直达那一家：点进去就是这家酒店、这趟航班组合或这个团，日期、人数、房间数和币种都已填好，不用再搜。酒店用平台的详情页，不用城市搜索页或按名字搜的结果页（会混进别家，排序也乱）：
  - Booking.com `https://www.booking.com/hotel/<国家码>/<slug>.html?checkin=YYYY-MM-DD&checkout=YYYY-MM-DD&group_adults=2&no_rooms=1&group_children=0&selected_currency=CAD`
  - Expedia `https://www.expedia.ca/<城市>-Hotels-<名字>.h<ID>.Hotel-Information?chkin=YYYY-MM-DD&chkout=YYYY-MM-DD&rm1=a2`
  - Trip.com `https://ca.trip.com/hotels/detail/?hotelId=<ID>&checkIn=YYYY-MM-DD&checkOut=YYYY-MM-DD&adult=2&crn=1&curr=CAD`
  - Vio `https://www.vio.com/Hotel/Search?hotelId=<ID>&checkIn=…&checkOut=…`
  slug 和 ID 从平台搜索结果里该酒店的链接取，打开核对名字和地址（同名酒店、旧名很常见）。找不到详情页时退而用搜索页，并在 note 里说明。`validate_trip.py` 看到搜索页或首页链接会提醒。
- 套餐拆分用的单买参考价也取各平台最低，并且同口径（同晚数、同人数、都含税）。

## 限制与特殊日期

可以正常行走上下车但不登山：保留正常参观、驾车和车览，山顶步道可替换为外围观景，并明确不是登顶。浮潜与脚蹼使用依本人已有康复建议、现场指导及海况，不给医学许可保证。

冬季北岸等风险核对当地管理机构资料；不能用「上午通常平静」保证冬季能下水。区分到访海湾与在那里浮潜：岸边到访可以保留，下水移到合适地点。末日浮潜要核对实际航班和补做窗口，不与水肺潜水混为一谈。

按周几、周休、节假日、特别营业、预约、晚秀与回程核对日程。往年烟花公告不是本年度确认，常规大秀不是跨年特别节目。冲突的晚餐、文化村与游船只能是替换方案。

## 一天怎么排

1. **先放锚点。** 要预约、有固定场次的团、演出、船班先定位置，其他围绕它排。开门早的放早上，关门早的往前放。一圈路线选顺时针还是逆时针，要同时满足开门时间、场次和关门时间。
2. **每段都用路网核对。** 用缓存道路的分段估时检查：下一项开始时间至少等于上一项结束时间加车程，再留停车、签到的余量（团一般提前15–20分钟到）。改了顺序或地点，就重新抓路线再核一遍。
3. **查关门，不只查开门。** 要查闭园、末班车、最后入场和最后一班船。官网没写的，按关门前留足时间到达，在待办清单里加「出发前打电话确认」，并写好末班较早时的备选顺序（例如先走迷宫再坐车）。
4. **用户点名要玩的先保时长。** 时间不够时按用户给的优先级取舍：先去掉可选项，再压缩短停留，再略过当时条件不好的地方（例如冬季下午北岸大浪时的海湾）。去掉了什么、为什么，要告诉用户。
5. **当天最后一项不确定时，标成可选。** 例如顺路的奥莱，并写明不去时几点能回到住处。
6. **删掉的地点要全部同步。** 地图点、每日路线、分享海报贴纸、待办清单和门票预算一起删改，不留下不去的点。
7. **傍晚和夜间活动。** 日落、出海、烟花、观星要核对当地日落时间、月相（新月前后最暗）、季节海况，以及每周固定活动是否照常。最后一天还要倒推去机场的时间。

## 旧攻略项目覆盖

只在用户给了旧攻略（PDF、截图、以前的行程）时做；从零做的攻略不写 `coverage`。

提取所有地点、体验、餐厅和备选，去重后区分必去、在该地点的替代玩法、有空才做。三个牧场tour备选不等于全买。按最新要求取消冲浪、替代hiking，并展示覆盖表：原项目 → 日期/替代/取消/备选 → 解释。

不能静默遗漏。五晚不变但项目增加时，说明紧凑度、迷宫等排队可选项、错过的表演、预算上涨，不假装与原资料建议的每项整天等价。私人行程、健康描述、驾照信息和订单不作为公开demo fixture。
